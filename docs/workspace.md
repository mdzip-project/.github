## Review notes

Things the scan turned up that need a human decision — please resolve
during review:

1. **Windows preview duplicate — resolved.** The personal-namespace
   clone `mdzip-win-preview` was moved to `../archive/` on 2026-06-26;
   `mdzip-win-prev` (`mdzip-project/mdzip-win-prev`) is the canonical
   handler. The redundant `mdzip-project/mdzip-win-preview` GitHub repo
   was **archived** on 2026-06-26 (optionally hard-delete it later).

2. **Stale local remotes (not an ownership split).** Every repo
   already lives in the `mdzip-project` org. Three local clones —
   `mdzip-core-js`, `mdzip-cli`, `mdzip-win-preview` — had `origin`
   pointing at the old personal `kylemwhite/mdz-*` URLs. Those
   were transferred/renamed on GitHub, which keeps a redirect, so fetch
   and push still reach the right place. The redirect is fragile (it
   breaks if anything is later created at the old path), so update them:

   Updated 2026-06-26 for `mdzip-core-js` and `mdzip-cli`:

   ```sh
   git -C ../mdzip-core-js remote set-url origin https://github.com/mdzip-project/mdzip-core-js.git
   git -C ../mdzip-cli     remote set-url origin https://github.com/mdzip-project/mdzip-cli.git
   ```

3. **Repos without `package.json`** (`mdzip-cli`, `mdzip-core`,
   `mdzip-mark`, `mdzip-spec`, `mdzip-win-prev`) have no machine-readable
   dependency data, so their **deps** tile will read `n/a`. If any
   couples to a spec/manifest version (e.g. the preview handler to the
   `.mdz` format), declare it explicitly later per the `DEPENDENCIES.json`
   plan.

4. **Roles marked `(confirm)`** were inferred from folder names/READMEs
   with no clear description: `mdzip-mark` and the preview handler
   `mdzip-win-prev`. (`mdzip-core`'s role is now confirmed as the C#
   core library.)

5. **`mdzip-cli` → `mdzip-core` is a NuGet coupling.** `mdzip-cli`
   consumes the `MDZip.Core` package (currently `1.4.0`; renamed from
   `mdzip-core` 2026-07-08, see
   [nuget-mdzip-core-rename.md](nuget-mdzip-core-rename.md)) via a C#
   `PackageReference`, not an npm dependency or a project reference.
   The dashboard can't auto-compute "behind" for it (no
   `package.json`); the version lives in
   `mdzip-core/src/mdzip-core/mdzip-core.csproj` (`<Version>`) — the
   repo and file paths keep the old `mdzip-core` name, only the
   published package ID changed. This is the kind of non-npm coupling
   the `DEPENDENCIES.json` enhancement is meant to make
   machine-readable.

6. **.NET 10 upgrade — committed on branches, not merged.** Both repos have
   an `upgrade/net10` branch at **v1.2.0**: `mdzip-core` multi-targets
   `net8.0;net10.0` (`b4b392b`), `mdzip-cli` targets `net10.0` (`4dac987`).
   Release ordering and the next step (publish core 1.2.0, then bump cli's
   `mdzip-core` reference) are tracked in [roadmap.md](roadmap.md); the
   integration-test recipe is in [dotnet-workflow.md](dotnet-workflow.md).
